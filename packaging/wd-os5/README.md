# HSYNC — WD My Cloud OS5 Package

This directory holds everything needed to build a `.bin` installer for the
**Western Digital My Cloud EX2 Ultra** (and other OS5-based My Cloud devices)
that can be installed through the stock admin Dashboard
(`Apps → Install an App manually`).

The package wraps the standalone `hsync` PyInstaller binary together with a
small web UI for configuring the service, controlling it (start/stop/restart)
and viewing its runtime log — all without SSH access.

## Target

| Item              | Value                                              |
| ----------------- | -------------------------------------------------- |
| Device            | WD My Cloud EX2 Ultra                              |
| SoC               | Marvell Armada 385 (Cortex-A9, dual-core 1.3 GHz)  |
| Architecture      | ARMv7 32-bit hard-float (`armv7l` / `armhf`)       |
| Firmware          | Stock My Cloud OS 5                                |
| glibc on device   | up to `GLIBC_2.30` (verified on firmware 5.x)      |
| Build base image  | `debian:buster` (`arm32v7`) — `glibc_2.28`         |
| Python on device  | not required (PyInstaller `--onedir`, standalone)  |

The build base is **Debian 10 (buster)** so the produced binary depends only
on `GLIBC ≤ 2.28`, which is comfortably below the `2.30` ceiling exposed by
the stock OS5 firmware.

## Build flow

The builder image bakes the third-party dependencies **and** the application
sources as cached layers, so the slow ARMv7 native compilation (a static
OpenSSL 3, cryptography, zstandard, the PyInstaller bootloader) happens once at
`docker build` time instead of on every run. Editing application code rebuilds
only the cheap source layers and reuses the cached dependency install; the
per-run container does nothing but produce the frozen binary.

```
host (x86_64)                    qemu-user-static (armv7)
─────────────                    ────────────────────────
compile.sh --target wd-ex2-ultra-os5
    │
    ├── stage build context ───────────────► build/wdos5/ctx/
    │       (hsync-client + hsync-common manifests & sources)
    │
    ├── docker build -f Dockerfile.builder ──► hsync-wdos5-builder:armv7
    │       debian:buster + Python 3.12 + Rust + static OpenSSL 3 + Poetry
    │       + poetry install (deps, cached layer) + baked sources
    │
    ├── docker run … pyinstaller --onedir ──► build/wdos5/bin/hsync/
    │       (deps already installed; only the binary is produced)
    │
    ├── generate icon  ─────────────────────► Apkg/hsync.png
    │
    ├── stage Apkg/ + binary + apkg.rc ────► build/wdos5/hsync/
    │       (apkg.rc has __HSYNC_VERSION__ replaced by pyproject version)
    │
    ├── docker build -f Dockerfile.mksapkg ──► hsync-wdos5-mksapkg:bullseye
    │       debian:bullseye + libxml2.so.2 + OpenSSL 1.1.1 (bf-cbc)
    │
    └── docker run … mksapkg-OS5 -E -s -m MyCloudEX2Ultra
            │       (staging parent mounted at /work; cached tool bind-mounted)
            └─► dist/wd-ex2-ultra-os5/MyCloudEX2Ultra_hsync_<ver>.bin
```

The source `Apkg/` tree is **never mutated** by the build: the binary and
the rendered `apkg.rc` are written to a disposable staging copy under
`build/wdos5/hsync/`, and `mksapkg-OS5` packs that copy.

`mksapkg-OS5` itself runs inside a small `debian:bullseye` container rather
than on the host: the prebuilt tool is linked against `libxml2.so.2` and shells
out to `openssl bf-cbc` to sign `apkg.sign`, neither of which modern hosts
provide (e.g. Ubuntu 26.04 ships libxml2 `.so.16` and OpenSSL 3 hides bf-cbc
behind the legacy provider). The container carries both, so packaging is
reproducible regardless of the host distribution.

## Runtime layout on the NAS

| Path                                            | Purpose                                       |
| ----------------------------------------------- | --------------------------------------------- |
| `/shares/Volume_1/Nas_Prog/hsync/`              | Installed package (binary, scripts, web)      |
| `/mnt/HD/HD_a2/hsync/data/`                     | Default synced directory (user-configurable)  |
| `/mnt/HD/HD_a2/hsync/config/hsync.env`          | Persistent configuration written by the UI    |
| `/mnt/HD/HD_a2/hsync/log/hsync.log`             | Runtime log (rotated by the OS)               |
| `/mnt/HD/HD_a2/hsync/state/server/<bucket>.db` | Causal versions and tombstones, one per bucket (outside the synced folder) |
| `/var/www/hsync/`                               | Symlinks to `Apkg/web/*` for the admin UI     |

The config path lives on the data volume so it survives package re-installs
and firmware upgrades.

## Configuration

The web UI exposes the options of the HSYNC desktop application, each mapped
1:1 to a `hsync` CLI flag (or to the environment variable for the knobs that
have no flag). The defaults are seeded by `Apkg/install.sh` and mirrored by the
fallbacks in `Apkg/start.sh`, with one deliberate exception: the NAS is a
**backup target**, so it ignores client-side deletions and the backup never
loses files because a source host removed them. Adjust everything from the UI
for other use cases.

The p2p transport is **HTTPS/WSS-only** (protocol `p2p/1`): the master serves
over TLS with a persistent self-signed identity and advertises its certificate
fingerprint, which the peers pin (Trust-On-First-Use). There is no plain-HTTP
option to configure.

| UI field            | CLI flag / environment                         | Default                          |
| ------------------- | ---------------------------------------------- | -------------------------------- |
| Sync folder         | `-p / --path`                                  | `/mnt/HD/HD_a2/hsync/data`       |
| Mode                | `hsync p2p` vs `hsync server`                  | p2p                              |
| Share name          | `-b / --bucket`                                | `my-bucket`                      |
| Sync type           | `--sync-direction`                             | bidirectional                    |
| Subfolder           | `--subdir`                                     | _empty_ (whole share)            |
| Extra ignore patterns | `--ignore-pattern` (repeated)                | _empty_                          |
| Ignore rules editor | `.hsyncignore` at the share root               | _empty file_                     |
| Keep deleted files  | `--ignore-delete`                              | on (backup target)               |
| Compression         | `--no-compression` when disabled               | enabled                          |
| Delta transfer      | `--no-delta` when disabled                     | enabled                          |
| Simulation mode     | `--dry-run`                                    | off                              |
| Periodic full check | `-i / --interval` (`0` = `HSYNC_RESYNC=0`)     | `0` (disabled)                   |
| Wait before retry   | `--retry-delay`                                | `5` s                            |
| Wait for file to settle | `--stability-delay`                        | `5` s                            |
| Maximum wait        | `--max-wait-timeout`                           | `120` s                          |
| Request timeout     | `--http-timeout`                               | `30` s                           |
| Auto-tune           | `--no-autotune` when disabled                  | on                               |
| Max concurrent transfers | `--max-concurrent-transfers`              | `0` (auto)                       |
| Delta minimum size  | `--delta-min-file-size` (edited in KB)         | `256` KB                         |
| Delta minimum size p2p | `--delta-min-file-size-p2p` (edited in KB)  | `1024` KB                        |
| Upload / download limit | `--limit-upload` / `--limit-download`      | unlimited                        |
| Min free disk space | `--min-free-disk-space`                        | `500MB` (size string, `0` = off) |

| Deletion protection | `--no-mass-delete-guard` when disabled         | on                               |
| Max deletions per cycle | `--mass-delete-threshold`                  | `50` (`0` = off)                 |

| p2p group           | `--group`                                      | `my-group`                       |
| Shared password     | `HSYNC_P2P_PASSPHRASE` env var                 | random 24-character value at install |
| Port                | `--listen-port`                                | `0` (auto)                       |
| Download from other devices | `--no-peer-download` when disabled     | on                               |
| Max simultaneous reads | `HSYNC_P2P_PEER_READ_CAP`                   | `2`                              |
| Max devices per file | `HSYNC_P2P_PEER_SOURCES_MAX`                  | `3`                              |
| Device search timeout | `--discovery-timeout`                        | `10` s (5-60)                    |
| Discovery server    | `HSYNC_BOOTNODE` env var                       | _empty_ (local discovery only)   |
| Discovery server extra UDP ports | `HSYNC_BOOTNODE_PORTS` env var    | _empty_ (single-port dialing; e.g. `53`) |
| Discovery server fingerprint | `HSYNC_BOOTNODE_FINGERPRINT` env var  | _empty_ (no pin)                 |
| Discovery server TOFU | `HSYNC_BOOTNODE_TOFU` env var               | `false`                          |
| Discovery server identity check | `HSYNC_BOOTNODE_TRUST` env var     | `ask`; `ask`, `accept-new`, `strict`, `none` |
| Router port mapping | `HSYNC_UPNP_ENABLED` env var                   | on (only with a discovery server) |
| Time servers        | `HSYNC_NTP_HOSTS` env var                      | client defaults (p2p clock offset) |
| Server address      | `HSYNC_SERVER` env var                         | _empty_                          |
| API key             | `HSYNC_API_KEY` env var                        | _empty_                          |
| Skip certificate check | `--insecure`                                | off (excludes a pin or TOFU)     |
| Certificate authority file | `--ca-cert` (upload stores `config/ca.pem`) | _empty_                    |
| Server identity check | `HSYNC_SERVER_TRUST` env var                 | `chain`; `chain`, `ask`, `accept-new`, `strict`, `none` |
| Server fingerprint  | `HSYNC_SERVER_FINGERPRINT` env var             | _empty_ (no pin)                 |
| Server TOFU         | `HSYNC_SERVER_TOFU` env var                    | `false`                          |
| Detailed log output | `-v / --verbose`                               | off                              |
| Quiet               | `--quiet`                                      | off                              |
The role is expressed with the same two switches as the desktop:

| Control                | Flag                | Meaning                                         |
| ---------------------- | ------------------- | ----------------------------------------------- |
| Prefer primary role    | `--prefer-master`   | this device coordinates the group when possible |
| Never become primary   | `--never-master`    | syncs both ways but never takes the primary role |

Both are off by default, so election decides. "Prefer primary" is applied only
for a bidirectional sync: the client rejects that pair with a one-way direction.

Four actions delegate to the packaged binary and therefore share its trust
stores and state directory: **Test Connection** and **Test discovery server**
(`hsync trust server|bootnode fingerprint`), **Manage trusted servers &
devices** (`hsync trust <kind> list|add|remove`) and **Reset sync state**
(`hsync state reset --folder … --quarantine`, executed with the service
stopped).

## Connect another device

When the NAS runs in **p2p mode**, the web UI shows a live-generated
`hsync` command under a **Connect another device** section. Run that command
on another device to join the sync group coordinated by the NAS instead of
assembling the flags by hand.

The command is built client-side from the current form values and contains
only the connection-matching fields. It is recomputed whenever the share name,
group or shared-password fields change, and after pressing **Save** it is
rebuilt from the configuration actually persisted by the backend (which
normalizes inputs such as an invalid share name or boolean fields), so the
command always matches what the NAS runs with:

```
HSYNC_P2P_PASSPHRASE='<masked>' hsync p2p -b '<share>' -p '<local-folder>' [--group '<group>']
```

- `<share>` and `--group` mirror the NAS settings so the peer can find the
  group; `<local-folder>` is a placeholder for the folder to sync on the other
  device. Every interpolated value is POSIX single-quoted, so the command is
  safe to paste even if a value contains `$`, `"`, backticks, or spaces.
- The shared password (when set) is shown **masked** with a *Show password*
  toggle; the *Copy* button copies the full command including the real value.
  The field requires **at least 12 characters**: the client derives the 32-byte
  group key with scrypt, so the same password is all the other device needs (no
  long key to type). The value generated at install is a random 24-character
  password from the desktop client's unambiguous alphabet, so the default is
  already compliant and easy to transfer.
- Per-device sync behaviour (keep deleted files, compression, delta,
  bandwidth, …) and the NAS role are intentionally omitted: continuous mode
  is the default in both p2p and server mode, and primary election resolves
  the remote device's role automatically.

In **server mode** the NAS is itself a client of a central `hsync-server`, so
there is no direct "connect to the NAS" command; the section shows a note
explaining how to point another device at the same server and share.

## Maintenance

The **Reset sync state** button stops the service, runs
`hsync state reset --folder <shared folder> --quarantine --json` with the same
`HSYNC_STATE_DIR` that `start.sh` exports, and starts the service again. Only
the folder's merge bases and deletion markers are dropped: synced files, the
shared password, the device identity and the trusted fingerprints stay
untouched. The next cycle re-scans the share, so the first sync is slower and
files deleted shortly before the reset can come back.

The **Manage trusted servers & devices** panel lists and edits the same trust
stores (`hsync trust bootnode|server|peer list|add|remove`), while
**Test Connection** and **Test discovery server** read the peer certificate
fingerprint (`hsync trust … fingerprint`). Every action runs the packaged
binary with the service's state directory, so it behaves exactly like the same
command on the NAS shell.

## Locales

The web UI ships with the same eleven locales as the desktop client:
**EN, IT, DE, ES, FR, JA, NL, PL, PT, RU, ZH**. Language is auto-detected from
`navigator.language` and can be overridden from the UI header. The language list
is defined once in `Apkg/web/app.js` (`SUPPORTED`); every entry must have a
matching `Apkg/web/i18n/<code>.json` dictionary (enforced by the test suite).

## Log viewer

The **View log** button opens an overlay that tails the runtime log at
`/mnt/HD/HD_a2/hsync/log/hsync.log` in near real time. The browser polls
`log_get.php`, which returns only the bytes appended since the last byte offset
it received, so updates feel live without re-transferring the whole file; the
first load shows the tail window (last 64 KiB) and each poll is capped (256 KiB)
so a write burst cannot return an unbounded payload. The endpoint is read-only
with a fixed path (no user input selects the file). The overlay offers
**Auto-scroll**, **Clear** and **Close**; polling stops when the overlay is
closed.

## Notes for maintainers

* The package **version** is taken from `pyproject.toml` at build time and
  injected into `Apkg/apkg.rc`. There is no separate version to bump here.
* The `mksapkg-OS5` tool is fetched from the upstream
  [WDCommunity/wdpksrc](https://github.com/WDCommunity/wdpksrc) repository
  the first time `compile.sh --target wd-ex2-ultra-os5` runs and cached
  under `packaging/wd-os5/.cache/`.
* **Containerized mksapkg.** The cached tool is executed inside the
  `hsync-wdos5-mksapkg:bullseye` image (built locally from
  `Dockerfile.mksapkg`, not published to any registry) rather than on the host.
  The prebuilt x86-64 binary links against `libxml2.so.2` and signs `apkg.sign`
  by shelling out to `openssl bf-cbc`; Debian Bullseye still provides both,
  whereas modern hosts ship libxml2 `.so.16` and gate bf-cbc behind the OpenSSL
  3 legacy provider. The staging dir's parent is bind-mounted at `/work` (since
  `mksapkg-OS5` drops the `.bin` in the parent of its CWD) and the container
  runs as the host uid so artifacts stay caller-owned.
* The builder image is built locally and is **not** published to any
  registry. Re-run `compile.sh --target wd-ex2-ultra-os5 --clean` to force a
  rebuild.
* **Host-uid PyInstaller.** The `docker run … pyinstaller` step runs as the
  host uid (`-u "$(id -u):$(id -g)"`, with `HOME`/`XDG_CACHE_HOME` pointed at
  `/tmp` so the cache is writable) so the bundle it writes to `build/wdos5/`
  stays caller-owned. Otherwise PyInstaller would run as root and the later
  `build/` cleanup of a plain `./compile.sh` (native) build would fail with
  *Permission denied*.
* The **dependency install** is a cached Docker layer keyed on
  `pyproject.toml` + `poetry.lock` (for both `hsync-client` and the
  `hsync-common` path-dependency). It is recompiled only when those manifests
  change; editing application code reuses the cached layer and rebuilds only
  the cheap source layers. The slow ARMv7 native build (cryptography,
  zstandard, the PyInstaller bootloader) therefore happens once and is
  persisted by BuildKit, surviving interrupted runs.
* **OpenSSL 3 (ARMv7).** `cryptography` (pinned `>=48,<50`, resolving to
  49.0.0) refuses to compile against OpenSSL < 3.0.0, but Debian Buster ships
  only 1.1.1. The builder therefore compiles a **static** OpenSSL 3
  (`OPENSSL_VERSION` in `Dockerfile.builder`, SHA256-pinned) into
  `/opt/openssl3` and points the Rust `openssl-sys` build at it via
  `OPENSSL_DIR` + `OPENSSL_STATIC=1`, so the `cryptography` extension embeds
  OpenSSL 3 statically and the bundle stays self-contained on the NAS. The
  CPython `ssl` module keeps using the system libssl 1.1.1. Bumping
  `OPENSSL_VERSION` requires updating `OPENSSL_SHA256` in lock-step. On amd64
  this layer is unused (prebuilt manylinux `cryptography` wheels apply).
